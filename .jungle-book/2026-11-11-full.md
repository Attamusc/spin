# Jungle-Book: Full Codebase

**Date:** 2026-11-11  
**Scope:** All application packages, command adapters, colocated tests, README, project conventions, Makefile, module manifest, and current status contract; historical plans used only as context. Generated binaries and VCS internals excluded.  
**Prior run:** None  
**Baseline:** Parent revision `d77cc8fd`; application source unchanged by this analysis.

## Glossary

- **Pattern** — a recurring shape in code, naming, abstraction, layout, or data flow.
- **Friction** — resistance the codebase creates against change.
- **Creep** — a gap that is not hurting today but trends toward decay.
- **Signal** — how clearly a pattern communicates its intent to a new reader.
- **Drift** — divergence between things that should follow the same pattern.
- **Grain** — the natural direction of change in the codebase.

Risk labels: **Active** means the current implementation exhibits the problem; **Creeping** means an observed gap makes future changes riskier; **Dormant** means a policy decision is needed, without evidence of ongoing decay. Active does not imply an incident occurred in actual user data.

## Summary

**Patterns found:** 6 positive · 11 negative · 4 inbetween

**Grain:** This is a small Go CLI with useful package boundaries and a straightforward command-per-file structure. Adding commands is easy; changing shared identity, lifecycle, and filesystem behavior is harder because those policies are independently reconstructed in several places.

**Verdict:** Keep Go, Cobra, TOML, and the small internal packages. Modernization should make destructive operations safe, give commands reliable results, and extend the status implementation's explicit boundaries and executable tests—not introduce a framework or rewrite the application.

**Top 3 priorities:**
1. **N1 — SQLite files treated as ordinary files** (negative): a successful restore can still expose the previous data → [N1](#n1--sqlite-files-treated-as-ordinary-files).
2. **N2 — Lifecycle trusts unvalidated PID integers** (negative): malformed PID values can reach process-group/broadcast signal semantics → [N2](#n2--lifecycle-trusts-unvalidated-pid-integers).
3. **N3 — Unvalidated names become writable paths** (negative): project creation and snapshots can escape their intended roots → [N3](#n3--unvalidated-names-become-writable-paths).

## Positive

### P1 — Small domain packages behind a thin entrypoint

- **Where:** `main.go:9-13`; `internal/{config,db,discovery,process,resolve,shell,template,vcs}/`; `cmd/open.go:58-95`.
- **What:** Internal packages own config, discovery, resolution, process execution, VCS, copying, and shell generation. The entrypoint delegates to Cobra.
- **Signal:** Strong — most behavior has an obvious package owner.
- **Grain:** With — new command adapters can reuse these operations.
- **Drift:** Some policy remains in command handlers, especially lifecycle coordination and status collection.
- **Leverage:** SQLite backup behavior can change inside `internal/db` without replacing the CLI framework.

### P2 — Status separates evidence, diagnostics, and rendering

- **Where:** `cmd/status_collect.go:16-101,125-344`; `cmd/status.go:25-91`; `docs/status-contract.md:5-130`.
- **What:** Status returns explicit states, nullable metadata, completeness, sorted diagnostics, and versioned JSON. Rendering does not perform lifecycle cleanup; permission failure is not treated as proof of death.
- **Signal:** Strong — uncertainty and effects have a declared contract.
- **Grain:** With — additional consumers can render the same observation.
- **Drift:** Older discovery and lifecycle helpers still collapse or suppress uncertainty.
- **Leverage:** A status output change can reuse one collector and preserve its read-only guarantee. Reuse the result pattern elsewhere, not necessarily the v1 wire types.

### P3 — Narrow test seams rather than a mocking framework

- **Where:** `cmd/status_collect.go:43-60`; `cmd/open.go:32-55`; `cmd/open_test.go:10-80`; `cmd/status_collect_test.go:103-250`.
- **What:** Dependencies such as PID probes, clocks, directory reads, and browser runners can be replaced with small functions.
- **Signal:** Strong — tests explicitly control the source of uncertainty.
- **Grain:** With — platform and failure behavior can be tested without affecting the host.
- **Drift:** Most other commands use globals and direct OS streams.
- **Leverage:** EPERM and output failures are testable without manipulating actual process permissions or opening a browser.

### P4 — Executable contracts and isolated fixtures

- **Where:** `cmd/status_integration_test.go:24-218`; `cmd/status_cli_test.go:12-82`; `cmd/list_cli_test.go`; `internal/*/*_test.go`.
- **What:** Tests use temporary trees; status subprocess tests verify streams, exits, non-mutation, secret exclusion, and no incidental tool execution. Shell cache tests execute generated functions under zsh.
- **Signal:** Strong — assertions state observable behavior, not only implementation shape.
- **Grain:** With — command refactors can retain user-visible guarantees.
- **Drift:** Database tests mostly check byte copying rather than SQLite behavior.
- **Leverage:** A collector rewrite can be checked against the same before/after filesystem manifest.

### P5 — Bounded directory discovery and shared project inventory

- **Where:** `internal/discovery/scan.go:34-119`; `cmd/list.go:37-54`; `cmd/go.go:48-60`.
- **What:** Discovery reads exactly host/owner/repo levels rather than recursively walking every repository. Configured discovery filters the all-project inventory.
- **Signal:** Strong — cost follows the project layout, not repository contents.
- **Grain:** With — both navigation and configured commands can use one inventory.
- **Drift:** Resolver exact-match paths bypass the inventory's opportunity to detect cross-host duplicates; discovery suppresses nested read failures.
- **Leverage:** Adding a repository does not require parsing its source tree or running VCS commands.

### P6 — Small dependency surface and declared platform scope

- **Where:** `go.mod`; `Makefile:18-59`; `README.md` install/development sections; `internal/vcs/vcs.go:26-105`.
- **What:** Go, Cobra, TOML, color output, and small standard-library packages cover the application. VCS subprocesses reserve stdout for command data; jj-first/git-fallback is an intentional product behavior.
- **Signal:** Strong — the build is understandable without a service framework.
- **Grain:** With — focused fixes do not require an architectural migration.
- **Drift:** Some conditional runtime tools are not documented accurately; see I3.
- **Leverage:** Existing targets already support tests, race detection, vet, formatting, and three successful target builds.

## Negative

### N1 — SQLite files treated as ordinary files

- **Where:** `internal/db/snapshot.go:15-54,69-81,95-115`; `cmd/db_copy.go:54-97`; `cmd/db_snapshot.go:63-75`; `cmd/db_restore.go:49-74`; `internal/db/snapshot_test.go:25-62,103-143`.
- **What:** Copy/snapshot checkpoint opportunistically, continue after checkpoint errors, and copy the main DB and sidecars separately. Restore truncates the destination in place, retains destination sidecars absent from the source, and permits overwriting an active dev DB because dev always reports not running. The checkpoint test creates an empty file, calls it a database, and discards the result.
- **Signal:** Weak — a success message does not establish that the restored logical contents are visible.
- **Grain:** Against — every new DB operation inherits filesystem semantics instead of SQLite consistency semantics.
- **Drift:** Live has a best-effort running guard; dev has none, and neither check serializes mutation against startup.
- **Risk:** `Active` — the isolated real-SQLite fixture returned successful restore while a new connection still saw the old destination WAL contents.
- **Migration path:** Follow **P1** and **P4**: give `internal/db` one SQLite-aware backup operation and an explicitly offline replacement operation. Use SQLite backup semantics for a changing source; require target quiescence/exclusive ownership before replacement or sidecar cleanup. Stage a verified replacement before publication, preserve close/write errors, and fail rather than warn-and-continue when consistency is unproven. Add real WAL fixtures, active-dev rejection, stale destination sidecars, busy/failed backups, and interrupted-write tests. There is **no positive SQLite-consistency exemplar** in this codebase; the actual backup protocol is a new convention. Choose its runtime mechanism under I3.

### N2 — Lifecycle trusts unvalidated PID integers

- **Where:** `internal/process/pidfile.go:22-59`; `internal/process/background.go:85-114`; `cmd/down.go:49-75`; compare `cmd/status_collect.go:191-209`.
- **What:** Lifecycle `ReadPID` accepts zero, negatives, and values outside signed pid_t range. `IsProcessAlive` collapses all errors to false; shutdown negates the value and can fall back to signaling it directly. A positive PID proves existence, not identity.
- **Signal:** Weak — the type `int` hides signal target semantics.
- **Grain:** Against — lifecycle and destructive DB guards need a trustworthy target, not a boolean existence guess.
- **Drift:** Status already rejects invalid values and preserves EPERM as unknown; lifecycle deliberately retained the older policy during that change.
- **Risk:** `Active` — PID 0 can lead to signaling the caller's process group, and negative targets can invoke broader kill semantics. Stale/reused positive PIDs can target unrelated processes. Source evidence only; dangerous signals were not tested.
- **Migration path:** Extend **P2/P3**'s validated positive signed-32-bit PID parsing and errno-aware probes into a separately tested lifecycle policy. Reject invalid signal targets at the process API boundary, not just in one caller. Unknown identity/permissions must not mean stopped or authorize destructive DB work. Before signaling, verify a recorded process identity appropriate to both supported OSes. Preserve the existing read-only status v1 contract; lifecycle hardening is a separate change. Test invalid values with injected signal functions, never real broadcast signals.

### N3 — Unvalidated names become writable paths

- **Where:** `cmd/new.go:48-98`; `cmd/clone.go:50-55,81-119`; `internal/db/snapshot.go:85-91`; `internal/config/project.go:53-59`; `internal/resolve/resolve.go:112-125,213-237`.
- **What:** Repo names, snapshot names, configured filename values, and host/owner values feed joins without a common validation policy. Extra separators and `..` are accepted in mutating paths; lexical cleanup is not containment enforcement.
- **Signal:** Weak — names appear to be identifiers but can act as paths.
- **Grain:** Against — adding a writable path requires rediscovering the same safety policy.
- **Drift:** CWD resolution checks lexical containment; creation and snapshot paths do not apply an equivalent boundary.
- **Risk:** `Active` — isolated `new o/../../../outside-new` escaped projects_root, and snapshot `../../../../escaped` escaped its snapshots directory, both with exit 0.
- **Migration path:** Use **P1/P3/P4** to establish one validated identity/name boundary before filesystem effects. Reject empty/dot/dot-dot/separator-containing components; validate URL shape separately rather than treating arbitrary URLs as path fragments. Keep intended relative paths distinct from single-component names. Root-scoped filesystem APIs such as Go's `os.Root` can strengthen writes against traversal and symlinks; they do not automatically secure subprocess working directories. Declare a symlink policy and test it, including cleanup paths. No positive root-confined mutation exemplar currently exists.

### N4 — Host is part of discovery identity but not storage identity

- **Where:** `internal/discovery/scan.go:10-17,89-95`; `internal/resolve/resolve.go:112-125,327-350`; `internal/process/pidfile.go:65-72`; `internal/config/project.go:53-59`; `cmd/status_collect.go:307-320`.
- **What:** Projects carry host/owner/repo, but PID/log/DB/snapshot paths use only owner/repo. Exact owner/repo resolution selects a matching host rather than requiring uniqueness.
- **Signal:** Ambiguous — display names and storage keys look identical but are not globally unique.
- **Grain:** Against — multi-host support cannot provide isolated lifecycle/data operations under the current key.
- **Drift:** Status detects ambiguity and leaves metadata unknown; normal resolution selects a host and storage aliases both projects.
- **Risk:** `Active` — same-named projects on two hosts share state paths; the observed exact lookup silently chose github.com.
- **Migration path:** Follow **P2/P5**: model identity once, collect all candidates, and require uniqueness. Decide between host-qualified storage/arguments and explicitly forbidding collisions; host-qualified identity fits existing discovery better. Inventory existing state and require an explicit migration decision for ambiguous data—do not guess a host or silently add legacy fallbacks. Add same-name/two-host command fixtures before changing paths.

### N5 — Command setup and global state impede focused tests

- **Where:** `cmd/root.go:14-27,30-71,76-96`; `cmd/dev.go:30-76`; `cmd/up.go:31-103`; `cmd/db_copy.go:32-96`; `cmd/status_collect_test.go:300-319`; `cmd/go.go:86-103`.
- **What:** Package-global Cobra objects, direct HOME/CWD/config access, direct OS writers, repeated load/resolve/prepare sequences, and `os.Exit` inside `runDev` make handlers difficult to exercise in-process. Two project completion functions currently contain the same ScanAll flow.
- **Signal:** Weak — handler dependencies and effects are implicit.
- **Grain:** Against — testing a new failure path often requires a full CLI subprocess or mutation of shared command objects.
- **Drift:** Status uses command writers and injected dependencies; most older commands bypass them.
- **Risk:** `Creeping` — adding commands multiplies copies and makes parallel test isolation harder.
- **Migration path:** Follow **P1/P3** incrementally: construct fresh commands, use `cmd.OutOrStdout`/`ErrOrStderr`, and pass a small concrete dependency bundle where tests need it. Centralize project selection and argument validation, but keep mutating preparation visibly separate. Return a typed exit result and let only `main` call `os.Exit`. Consolidate duplicate completion code while explicitly deciding configured-only versus all-project policy. Do not build a generic DI container or service layer for every command.

### N6 — Partial failure becomes success or apparent completeness

- **Where:** `cmd/update.go:98-138`; `cmd/new.go:107-112`; `internal/discovery/scan.go:60-75`; `internal/db/snapshot.go:57-66`; `internal/process/pidfile.go:43-52`; `cmd/down.go:60-75`.
- **What:** Bulk update prints failed results then returns nil; new warns on VCS failure then reports created success. Discovery omits unreadable nested directories; some stat/removal errors are ignored.
- **Signal:** Weak — exit 0 and an empty inventory can hide failed work.
- **Grain:** Against — automation cannot reliably distinguish complete from partial outcomes.
- **Drift:** Single-project update fails correctly; bulk update does not. Status explicitly models incomplete results.
- **Risk:** `Active` — fake git exit 42 produced bulk-update exit 0, versus exit 1 for the single-project command.
- **Migration path:** Apply **P2**'s partial-result-plus-diagnostics pattern to discovery and updates. Report successful work but return nonzero for incomplete requested work; `errors.Join` can aggregate failures without another dependency. Decide and document whether new-without-VCS is an allowed outcome rather than silently weakening its promise. Check non-ENOENT failures and required cleanup errors; use **P4** for CLI stream/exit tests.

### N7 — Lifecycle coordination is check-then-act

- **Where:** `cmd/up.go:48-61,86-95`; `internal/process/background.go:24-78,85-114`; `internal/process/foreground.go:39-59`; `internal/db/snapshot.go:71-81`.
- **What:** Up checks a PID file, then separately runs hooks, truncates logs, starts a process, and writes a PID. There is no common lock against another start or a destructive DB operation. Failed PID publication kills the leader without the normal wait path; stop polls leader liveness rather than proving descendants exited.
- **Signal:** Ambiguous — individual helpers are understandable, but ownership across a whole transition is unstated.
- **Grain:** Against — more lifecycle commands increase opportunities for races and incomplete cleanup.
- **Risk:** `Creeping` — simultaneous starts can both pass the check and publish different children; a DB guard can race startup; leader exit can leave descendants.
- **Migration path:** Use **P1/P3/P4** to establish one owner for per-instance transitions and a shared lock protocol covering starts and destructive DB work. Keep Setsid for detached processes and reap children; do not replace this with fork tricks. Test concurrent starts, failed PID publication, TERM-ignoring descendants, leader exit before descendants, and foreground signal forwarding. Track dev ownership if destructive commands are to reject active dev use. No positive serialized lifecycle exemplar exists yet.

### N8 — Long-running operations lack cancellation ownership

- **Where:** `internal/vcs/vcs.go:26-103`; `internal/process/foreground.go:22-81`; `internal/db/snapshot.go:15-25`; `cmd/update.go:82-108`; `cmd/logs.go:68-110`.
- **What:** VCS/checkpoint/hooks use exec.Command without contexts. Update limits active fetches to eight but allocates a goroutine per project; logs poll on a fixed sleep and install their own signal handler.
- **Signal:** Ambiguous — shutdown responsibility is distributed across helpers and subprocesses.
- **Grain:** Against — hung commands and cancellation require per-command special cases.
- **Risk:** `Creeping` — an authentication prompt, blocked checkpoint, or stalled remote can hold an operation indefinitely.
- **Migration path:** Use **P3** for explicit context-aware runners and **P6** to keep the implementation small. Connect foreground command cancellation to `cmd.Context`, make update scheduling stop on cancellation, and test a hanging fake command. A fixed worker pool can bound goroutines if project counts justify it. Treat detached up differently: its child must survive the CLI's exit; do not naively attach it to a request context. Preserve deliberate process-group signal policy rather than assuming CommandContext kills a whole tree.

### N9 — Generated shell code treats data as shell syntax

- **Where:** `internal/shell/zsh.go:18-34,78,108-144,159-164,204,223`; `internal/shell/zsh_test.go:24-44,181-303`.
- **What:** The executable path is interpolated unquoted; the picker assembles a shell command from a project name. The wrapper merges stderr into stdout to infer its final path and returns success after cd without checking cd's result. Tests mostly check text and cache-age functions, not full wrapper behavior.
- **Signal:** Weak — quoting and stream guarantees are implicit.
- **Grain:** Against — spaces, unusual names, and shell failures require patching scattered template sites.
- **Risk:** `Active` — a binary installed under a path containing spaces generated integration that failed with exit 127. Other injection/stream/cd cases are source-derived, not runtime-proven here.
- **Migration path:** Follow **P4/P6**: quote executable paths once for the target shell, pass picker selections as data or shell-quote them, preserve stderr as stderr, and propagate cd failure. Add zsh execution fixtures for spaces/quotes, stdout versus stderr, missing targets, failed cache refresh, and navigation failure. Retain atomic cache publication, but clean failed temporary files and test concurrent refreshes. Remove the unused git-clone wrapper alias unless it becomes a supported command.

### N10 — Verification can silently omit its strongest checks

- **Where:** `Makefile:43-59`; `internal/db/snapshot_test.go:25-62`; `internal/vcs/vcs_test.go`; repository root has no checked-in `.github/` CI configuration.
- **What:** Lint succeeds when staticcheck is absent, the only WAL test can skip, and even when run it ignores the operation result. VCS tests exercise relatively little successful subprocess behavior. No checked-in CI pipeline enforces a supported-platform matrix.
- **Signal:** Weak — a green local target does not say which checks actually ran.
- **Grain:** Against — regressions in the riskiest code can pass ordinary validation.
- **Risk:** `Creeping` — changes to DB consistency, subprocess behavior, or macOS signals have no dependable executable gate.
- **Migration path:** Build on **P4/P6**: add a small Linux/macOS CI matrix with explicit Go versions, vet, race tests where supported, required pinned staticcheck/govulncheck tooling, and required SQLite/zsh fixtures. Keep optional developer convenience separate from a strict CI check. Use fake PATH tools for deterministic argv/streams/exits and real SQLite for consistency; report skipped checks explicitly. Share a CLI build fixture and instrument child binaries when measuring command coverage. Prioritize destructive command acceptance tests over an arbitrary percentage target.

### N11 — Documentation describes intended rather than current behavior

- **Where:** `README.md` Quick start / Shell integration / Project resolution / Global config; `cmd/go.go:19-26,48-80`; `cmd/init_cmd.go:113-131`; `cmd/root.go:73-96`; `docs/status-contract.md:3-4`; `AGENTS.md` command-completion conventions.
- **What:** README/help promise a no-argument picker and clone prompt, while runGo prints a list or clone suggestion. The status document still says specification-only despite the implemented API; configured completion guidance differs from the shared ScanAll helper. Init advises ignoring a local `.spin/` even though current state is under projects_root.
- **Signal:** Weak — contributors cannot consistently tell which behavior is authoritative.
- **Grain:** Against — documentation-driven changes can reintroduce superseded assumptions.
- **Risk:** `Active` — users following advertised navigation behavior do not receive the described interaction.
- **Migration path:** Apply **P2/P4**: retain the status contract's schema/safety requirements but update its implementation-state header and clearly label historical baseline sections. Make executable CLI examples the current source of truth; align README/help/conventions with the chosen navigation and completion behavior. Do not implement old plan promises merely because they remain in a historical plan.

## Inbetween

### I1 — Two resolver families encode both useful policy and duplicated mechanics

- **Where:** `internal/resolve/resolve.go:34-41,96-211,256-450`; `cmd/root.go:98-134`.
- **What:** Config-required and directory-only resolution are useful distinctions, but each independently implements exact/fuzzy/ambiguous matching. Case rules differ; configured exact short-name matching uses equality while directory-only matching uses EqualFold. Completion has a separate fuzzy matcher.
- **Signal:** Ambiguous — deliberate policy and accidental implementation differences are interleaved.
- **Grain:** Ambiguous — the two APIs serve different needs but should not drift on identity.
- **Risk:** `Creeping` — fixing ambiguity or case behavior in one family can leave the other unchanged.
- **Migration path:** Follow **P5**: one candidate inventory and matching operation, with explicit configured/all and exact/fuzzy policies; load full config after selecting identity. Preserve semantic distinctions rather than replacing them with a universal flags-heavy resolver. Add cross-family contract tests before consolidation. Prefer exact-only selection for destructive commands unless fuzzy execution is deliberately accepted.

### I2 — Configuration parsing has not become a validation boundary

- **Where:** `internal/config/global.go:59-126`; `internal/config/project.go:28-59`; `cmd/status_collect.go:334-342`; `cmd/init_cmd.go:97-110`.
- **What:** Project loading validates commands but not DB filenames or port range. Status validates live ports separately; paths can remain relative outside the status normalization path. Unknown TOML keys are not rejected.
- **Signal:** Ambiguous — some invalid values fail at load time, others fail much later or are silently ineffective.
- **Grain:** Ambiguous — permissive config is convenient until effects depend on it.
- **Risk:** `Creeping` — a typo in an env/port key or an empty/escaping DB filename can reach an operational command without a clear validation error.
- **Migration path:** Extend **P1/P3** with explicit parse/default/validate stages, normalized roots, component validation, and unknown-key diagnostics. Keep path calculation pure; move directory creation out of a helper named ResolveProfileDBPath. Preserve **P2**'s partial status semantics: rejecting the entire config for an invalid port must not erase an otherwise observable PID row or uniquely matched identity. Test the stricter loader against the status contract before sharing it.

### I3 — SQLite runtime dependency is implicit

- **Where:** `internal/db/snapshot.go:13-25`; `internal/db/snapshot_test.go:25-31`; `AGENTS.md` Tech Stack; `README.md` Install / Version control / Shell integration.
- **What:** The application is mostly a standalone Go binary but WAL checkpointing requires sqlite3, navigation integration optionally uses zsh/fzf, and VCS work requires jj/git. sqlite3 was absent on this host, while instructions claim no other runtime dependencies.
- **Signal:** Ambiguous — users discover a conditional dependency only when its path runs.
- **Grain:** Ambiguous — subprocess-based SQLite is small; embedding a driver improves self-containment but adds binary/dependency cost.
- **Risk:** `Dormant` — choosing a backup implementation without deciding packaging constraints could produce another warn-and-continue path.
- **Migration path:** Follow **P6**: document required versus optional tools and preflight a required capability before destructive work. The smallest next step is an explicit sqlite3 dependency plus a tested backup protocol; choose a Go SQLite driver only if single-binary database operations are a product requirement. No positive SQLite backup implementation currently exists; a driver alone does not solve active-target safety.

### I4 — File-copy helpers lack an explicit link and failure policy

- **Where:** `internal/template/template.go:20-89`; `internal/template/template_test.go`; `internal/db/snapshot.go:95-115`; `cmd/new.go:72-112`.
- **What:** Template copying preserves file modes, but symlinks and other non-directory entries flow through os.Open; links may be dereferenced rather than preserved. Copy helpers defer destination closes without checking close errors; selected new-command failures remove the target, while other failures leave partial output.
- **Signal:** Ambiguous — basic recursive copying is clear, but link semantics and publication ownership are not.
- **Grain:** Ambiguous — adding templates with symlinks or generated assets will force a policy decision.
- **Risk:** `Creeping` — a linked file outside a template may be copied unexpectedly, special files may block, or partial output can be mistaken for a completed project.
- **Migration path:** Extend **P1/P4**'s template package and permission fixtures: choose preserve/reject/confine semantics for links, reject unsupported file types, validate templates before creating targets, and make cleanup ownership explicit. Create the final target exclusively or stage output before publication so cleanup never removes another operation's files. Reuse a low-level copy primitive only if semantics truly match; SQLite backup must remain separate from ordinary template copying.

## Recommended sequence

Effort below is relative scope, not a calendar estimate.

| Order | Work package | Scope | Acceptance evidence |
|---|---|---|---|
| 1 | Stop destructive surprises: N1–N3 | Medium–large; split into narrow fixes | Real SQLite WAL tests; invalid PID tests with fake signals; traversal/symlink rejection; no destination mutation on failed backup |
| 2 | Make identity unambiguous: N4 + I1 | Medium; storage decision/migration required | Two-host fixtures cannot share state or silently select a host; both resolver families agree on identity |
| 3 | Make commands testable and truthful: N5–N6 | Medium, incremental by command | Fresh command instances; no handler exits the test process; partial bulk failure exits nonzero; streams remain separated |
| 4 | Coordinate lifecycle/cancellation: N7–N8 | Medium–large | Concurrent start/DB mutation fixtures; process-tree shutdown tests; hanging subprocess cancellation; detached child survives normal up exit |
| 5 | Repair shell protocol and docs: N9 + N11 | Small–medium | Executed zsh fixtures for quoting/streams/cd failures; documented examples match behavior |

## What not to modernize

- Do not replace Cobra, TOML, or Go merely for newer alternatives; the evidence does not support a rewrite.
- Do not add a daemon, plugin framework, generic repository/service stack, or broad DI system to fix a handful of policy boundaries.
- Do not add packages solely to replace short standard-library code. Contexts, errors.Join, filesystem confinement, and ordinary command factories cover much of the work.
- Do not treat status as readiness or identity verification; its existing observation-only contract is deliberate.
- Do not conflate successful cross-compilation, skipped-tool tests, or byte-copy tests with runtime proof of process and SQLite behavior.
